# Component Guidelines (SOP §12, §14)

## Three-Layer Architecture

```
┌─────────────────────────────────────────────────┐
│  UI Layer (/components)                         │
│  • Pure presentational components               │
│  • Props in, callbacks out                      │
│  • No store, no API, no business logic          │
├─────────────────────────────────────────────────┤
│  Container Layer (/containers + /features)      │
│  • Connects business logic to UI                │
│  • Owns hooks for data fetching & state         │
│  • Passes prepared data to UI via props         │
├─────────────────────────────────────────────────┤
│  Business Logic (hooks + store)                 │
│  • Data handling, rules, state management       │
│  • Lives inside container hooks and store       │
│  • NEVER inside JSX                             │
└─────────────────────────────────────────────────┘
```

## UI Components (`/components`)

### Rules

- ✅ Render data received via **props only**
- ✅ Emit user interactions via **callback props**
- ✅ Use design tokens and theme values for styling
- ✅ Must be fully reusable across different contexts
- ❌ Must NOT access Redux store (`useSelector`, `useDispatch`)
- ❌ Must NOT import container hooks
- ❌ Must NOT make API calls
- ❌ Must NOT contain business logic or data transformation
- ❌ Must NOT hardcode data values

### Example — Pure UI Component

```jsx
// src/components/ui/unit-info-card/index.jsx
const UnitInfoCard = ({ unit, onClose }) => {
  // ✅ Only uses props
  // ✅ Emits callbacks
  return (
    <div className="...">
      <h3>{unit.name}</h3>
      <span>{unit.status}</span>
      <Button onClick={onClose}>Close</Button>
    </div>
  );
};
```

### shadcn/ui Components (`/components/ui/`)

These are framework-level primitives:

- `accordion.jsx`, `button.jsx`, `carousel.jsx`, `tabs.jsx`, `sheet.jsx`
- Auto-generated by shadcn/ui CLI
- Do NOT modify unless absolutely necessary
- Use `cn()` for variant composition

## Containers (`/containers`)

### Rules

- ✅ Connect business logic to UI components
- ✅ Own a container hook (`use-<name>.js`) for all logic
- ✅ Handle lifecycle events (`useEffect`)
- ✅ Pass prepared data and handlers to UI via props
- ❌ Must NOT contain business rules directly in JSX
- ❌ Must NOT contain UI-specific rendering logic (no complex JSX)
- ❌ Each screen/section must have a **single container entry point**

### Container Pattern

```jsx
// src/containers/inventory/index.jsx
import { useInventory } from "./use-inventory";
import InventorySidebar from "../../components/ui/inventory-sidebar";

const InventoryContainer = () => {
  const { units, filters, onFilterChange, onUnitSelect } = useInventory();

  return (
    <InventorySidebar
      {...{
        units,
        filters,
        onFilterChange,
        onUnitSelect,
      }}
    />
  );
};
```

## 3D Features (`/features`) — Project Exception

3D features are a **documented exception** to the strict container/UI separation because:

1. R3F hooks (`useThree`, `useFrame`, `useGLTF`) MUST run inside `<Canvas>`
2. Three.js objects cannot be passed as serializable props
3. Scene graph components are inherently coupled to the 3D context

### Feature Pattern (Already Correct)

```
features/building/
├── index.jsx           # Render component (pure scene graph)
└── use-building.js     # ALL logic: GLB loading, materials, pointer handlers, camera
```

### Feature Rules

- ✅ Direct store access is allowed in feature hooks (not separable)
- ✅ GSAP animations are allowed in feature hooks
- ✅ Three.js object manipulation is allowed
- ❌ Feature hooks must NOT render JSX
- ❌ Feature components must NOT contain logic beyond binding hook returns to JSX

## Common Components

Common components are pure UI building blocks shared across the app:

- Buttons, Inputs, Cards, Modals, Tooltips
- Must be 100% reusable
- No business logic
- No API calls
- Props must be clearly defined
- Styling must use design tokens only
